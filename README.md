# pg-relay 全套服务 → Cloady 部署包

把现在跑在本机 VM 上的两件套搬上 Cloady 免费工作区，换一个**固定不变**的
`*.cloady.io` 公网地址，摆脱 localhost.run 免费隧道的域名轮换。

## 包里是什么

| 文件 | 作用 |
|---|---|
| `Dockerfile` | 一体镜像：Node 24 + 中继源码 + 构建期下载的 AIStudio2API v0.3.12（sha256 双重校验） |
| `start.sh` | 容器入口：按环境变量生成全部配置，同时拉起无头执行器与中继，任一退出则整体退出让平台重启 |
| `app/` | 中继源码（`prepare.sh` 从 `../` 同步，只带运行必需的 11 个文件，约 540KB） |
| `prepare.sh` | 源码有改动后重跑，把 `app/` 刷新到最新 |
| `ENV.md` | 部署时要在面板填的环境变量清单 |
| `.dockerignore` | 构建上下文瘦身 |

容器内布局：`/app/relay`（中继，对外 18901）、`/app/headless`（执行器，
只监听 127.0.0.1:2048/2050，中继内部调用）。对外只暴露 18901 一个端口。

## 为什么不用「上传文件夹直传」省事

- 中继源码总共约 0.6MB，怎么传都行。
- 无头二进制解压后 **81MB**，超过 Cloady 上传文件夹的 **50MB** 上限，直传
  进不去。所以 Dockerfile 在构建时从 GitHub Release 下载官方 tar 包
  （33,972,508 字节），并用与现网生产二进制逐字节核对过的 sha256 校验
  （tar：`c44580d8…`；解压后二进制：`3f52551b…`，与本机在跑的那份完全相同）。
  部署包本体只剩约 0.6MB。

## 部署步骤（账号开通后）

1. **先选区**：永久免费档只有 **EU1（德国）/ USE1（美东）/ USW1（美西）**。
   注册后默认工作区落在 JPN1，那是 1 个月试用区，**部署前务必改区**。
   三个免费区都能直连谷歌；从国内访问延迟一般 USW1 相对好些。
2. **建应用**：部署来源选「上传文件夹」，传本 `cloady/` 目录（平台会按
   Dockerfile 构建）。注意：网页端「Docker 镜像」部署方式不能设端口和启动
   命令，别用那条路；走文件夹上传或 API deploy 端点（`port=18901`，
   启动命令即镜像 CMD，不用另填）。
3. **填环境变量**：按 `ENV.md` 填 4 个必填项（`PUBLIC_URL` 等拿到地址后再补）。
4. **挂持久卷**：见下一节，两个目录，部署前先挂好再首启。
5. **部署并验证**：起来后开 `https://<应用地址>/health`，应看到
   `"ok":true` 且 `"headless":{"enabled":true,"up":true,...}`。
6. **回填 `PUBLIC_URL`** 为应用的 cloady.io 地址，重新部署一次。
7. **切换使用**：从新地址的管理台下载脚本（地址已是新域名），篡改猴里
   覆盖安装；酒馆/App 的 API Base 改成 `https://<应用地址>/v1`，Key 不变。
   无头模式用小号在脚本里重推一次 Cookie 即完成账户迁移（账户数据在旧机
   上，不做 states.db 搬运——重推一次比搬库干净）。

## 数据持久化（重要）

容器文件系统在重新部署后会重置，以下两个目录**必须**挂 Cloady 持久卷，
挂载点与容器内路径一致：

| 容器内路径 | 内容 | 不挂的后果 |
|---|---|---|
| `/app/headless/runtime` | **已导入账户（states.db）**、请求/提示库、管理员会话、日志 | 每次重新部署账户全丢，要重推 Cookie |
| `/app/relay/data` | `pggo-state.json`：邮箱→自填代理绑定、上次推送结果；`owner.json`：站长口令哈希；`apikey-override.json`：站长改出的新服务 Key | 代理绑定和推送状态丢失（不致命，但要重填）；站长口令与改过的 Key 回退到部署时状态（口令需重设、Key 回到环境变量那把），不会锁死 |

其余配置文件（`config.json`、`headless.json`、`.env`、`current-url.txt`）
都由 `start.sh` 每次启动按环境变量重新生成，不需要持久化。
当前两处数据实际占用约 0.2MB，离 5GB 磁盘上限很远。

## 站长分层（owner）与自助改 Key

服务 Key 与管理台口令是两套凭据：

- **服务 Key**：只用来调 API（脚本、酒馆、手机 App）和 WS 执行器注册、
  Cookie 推送。拿到它的人能用服务，但**进不了管理台、改不了任何设置**。
- **站长口令**：站长本人首次打开管理台时在「站长区」自设（用当时的服务
  Key 验证身份，只存 scrypt 哈希于 `/app/relay/data/owner.json`，600）。
  设置后 `/api/console/*` 只认站长会话 Cookie（httpOnly，7 天有效；
  登录连错 5 次锁 5 分钟），服务 Key 再也进不了管理台。
- **自助改 Key**：站长登录后在管理台「站长区」可手动输入新 Key（≥16 位）
  或一键随机生成，新 Key 写入 `/app/relay/data/apikey-override.json`
  （600）并立即生效，旧 Key 作废；进程重启后仍以 override 为准。
  改完记得把脚本面板、酒馆、手机 App 里的 Key 一起换掉。
- **未设站长口令时**（如刚重新部署、数据目录被清）：管理台回退到服务
  Key 鉴权，站长用环境变量那把 Key 进去重新设口令即可，不会锁死。

## 资源申报与预算（免费档）

工作区里只放这一个应用，申报直接顶格免费档：

- **CPU 0.5 vCPU / 内存 1 GB / 磁盘 5 GB**（申报超出任何一项，整个工作区
  转全额计费，别超）。

内存实测账（本机实测数）：中继约 60MB + 执行器空载约 53MB + 预热第 1 个
账号约 150MB + 第 2 个约 55MB ≈ **常态约 320MB**；导入 Cookie / 同步模型
目录时有短时峰值，估算不超过约 550MB，1GB 申报有足够余量。
按月限额折算：内存 360 GB-小时 ÷ 720 小时 ≈ 允许平均常驻 0.5GB，
常态 320MB ≈ 230 GB-小时/月，在限额内（该项究竟按实际占用还是按申报
计量，官方口径不完全明确，上线后头几天瞄一眼账单页确认）。

其余月限额：出站流量 10GB、HTTP 请求 100 万次——纯文字聊天量级远远
用不到。**CPU 4 小时/月是最紧的一项**：无头执行每次生成要跑谷歌的
WAA 程序，是 CPU 密集型的；个人聊天量预计能装下，但上线后要观察，
真超了当月会停、下月 1 号自动恢复。另有 7 天无访问自动暂停：保持
正常使用即可，真被暂停去面板点 Start 恢复（脚本执行器在线时有 WS
长连接和心跳，不算「无访问」）。

## 已知差异（与本机部署相比）

- 中继监听地址：本机版绑 127.0.0.1（前面挡着隧道），镜像构建时改为
  默认 0.0.0.0（Dockerfile 里有锚点校验的 sed，源码改版导致锚点对不上
  会让构建直接失败，不会静默出错）。
- 无头出站：本机版借 VM 的 egress 代理，Cloady 版**直连**（`PROXY` 留空）。
  `start.sh` 还会主动清掉环境里继承来的代理变量并钉死 `NO_PROXY` 回环，
  防止平台注入的代理变量让中继拿代理打回环地址。
- 无头端口固定 2048：2049 是 Fetch 规范禁止端口（本地等效验证时实测
  踩过：中继 fetch 报 `bad port`、执行器永远显示离线），`start.sh` 已硬拦截。
- 没有 systemd：进程守护由 `start.sh` + 平台重启策略承担；没有隧道进程，
  也不再需要 `current-url.txt` 的看门狗（地址固定，`PUBLIC_URL` 填一次即可）。
